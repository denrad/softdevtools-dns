# Технический проект DNS-заявок

**Статус: проект, без работающей автоматизации.** Цель — безопасно обработать
заявки примерно 96 студентов в одной учебной DNS-зоне `softdevtools.ru`.
Репозиторий создаётся закрытым для подготовки и пилота; после проверки он
должен стать доступным студентам для fork и PR. Решение об открытии принимает
владелец репозитория после проверки содержимого и защиты ветки.

## Поток данных и границы доверия

```text
Студент: публичный сайт на Pages + PR с YAML
       → проверка PR без секретов
       → ручная сверка автора и одобрение преподавателя
       → merge в защищённую main
       → повторная проверка и DNS Edit через Cloudflare API
       → отдельная проверка DNS, HTTP и HTTPS
```

Автор PR и содержимое его ветки недоверенные. ФИО и контактный email поступают
через отдельный закрытый канал. Публичная заявка не служит доказательством
личности, а поле с самостоятельно указанным `github_id` не принимается как
доказательство владения поддоменом.

## Данные заявки: проект схемы

Один файл в `records/` описывает один CNAME на одно одноуровневое имя:

```yaml
subdomain: ivan
type: CNAME
target: ivan123.github.io
repository: https://github.com/ivan123/my-lab-site
```

В MVP разрешены только ASCII-метки из латинских букв, цифр и дефиса, без
дефиса по краям; только `CNAME` на `username.github.io`, DNS only
(`proxied=false`). Список зарезервированных имён задаётся преподавателем.
Не принимаются пользовательские A/AAAA/MX/TXT, wildcard, вложенные поддомены
и URL вместо DNS-имени. Окончательный предел длины метки и нормализация
регистра фиксируются в валидаторе и тестах.

Сопоставление `target`, владельца репозитория сайта и автора PR требует
отдельной проверки. Для уже принятого имени право изменения нужно закрепить
доверенными метаданными, которые студент не может назначить себе сам.
Точный формат этих метаданных пока не выбран; до его появления изменения
и удаление ранее принятых заявок не разрешаются автоматически.

## Проверка PR без секретов

Проверка должна давать конкретную причину отказа. Минимум:

1. Корректный YAML с известными полями и ровно одной заявкой.
2. Допустимое, не зарезервированное и ещё не занятое имя; отсутствие дублей
   внутри предлагаемого набора файлов.
3. Разрешённый тип и корректный `target`; ссылка на публичный репозиторий
   сайта имеет ожидаемую форму.
4. В студенческом PR изменяются только новые файлы в `records/`. Workflow,
   скрипты, конфигурация и уже принятые заявки недоступны для студенческой
   правки в этом процессе.
5. Проверки пересчитываются перед merge: два параллельных PR могут выбрать
   одно имя. Деплой повторно проверяет реальную зону и не перезаписывает
   неожиданную запись.

Проверка синтаксиса и структуры должна выполняться без сети и секретов.
Сетевые проверки GitHub Pages, DNS и HTTPS выполняются отдельно, когда
публикация уже началась. Проверка PR не ставит студенту итоговую оценку.

## Применение DNS

Деплой запускается только из защищённой `main` после принятия PR. Он повторно
валидирует доверенное состояние, сверяет запись с Cloudflare и создаёт либо
идемпотентно подтверждает только запись, которой управляет этот проект.
Чужие и созданные вручную записи не меняются и не удаляются. Удаление по
исчезновению YAML и полная синхронизация зоны в MVP не предусмотрены.

Cloudflare API Token хранится как GitHub Actions Secret или Environment
Secret и ограничен правом DNS Edit для одной зоны. Токен не попадает в
workflow проверки PR. Запуск секретного workflow зависит также от защиты
ветки и контроля изменений кода: хранение токена в Secrets само по себе не
защищает от вредоносного workflow после merge. До реальной записи нужен
`dry-run` на тестовых данных.

## Проверка результата и сроки

Проверяющий процесс хранит отдельные результаты:

| Проверка | Успех | Пока ожидается |
|---|---|---|
| `dns_live` | публичный CNAME равен ожидаемому | DNS ещё не виден через резолвер |
| `site_live` | HTTP или HTTPS отдаёт ожидаемый отличительный текст | Pages ещё не направляет имя на сайт |
| `https_live` | обычный HTTPS-запрос проверяет сертификат и текст | сертификат ещё выпускается |

Команда `curl -k` может помочь диагностировать страницу при ещё невалидном
сертификате, но не даёт статус `https_live=passed`. HTTP 200 без проверки
содержимого также недостаточен. Статусы результата: `passed`, `failed`,
`pending`, `not_checked`. Повторная проверка возможна без нового PR; расписание
не должно трактовать временную задержку DNS или сертификата как ошибку
студента.

На занятии достаточно подтвердить заявку, DNS и доступность именно нужной
страницы по HTTP либо HTTPS. Валидный HTTPS проверяется позже. Итоговое
понимание цепочки оценивает преподаватель.

## Пилот и незакрытые решения

- Проверить, что Cloudflare-зона активна и делегирована нужным NS.
- Пройти полный сценарий на двух разных аккаунтах GitHub. Подтверждение
  родительского домена в аккаунте преподавателя может заблокировать
  публикацию его непосредственных поддоменов из студенческих аккаунтов.
- Проверить сохранение Custom domain в Pages **до** добавления DNS-записи,
  затем CNAME, HTTP и HTTPS на практике.
- Выбрать механизм доверенного закрепления владельца поддомена и повторной
  проверки двух конкурирующих PR.
- Настроить доступные на текущем тарифе правила защиты `main`, reviews и
  обязательных проверок; проверить их на тестовом fork после открытия.
- Оценить, как очищать записи после курса. Для первого потока 96 заявок
  укладываются в бесплатный лимит зоны 200 записей с запасом для служебных
  записей, но накопление по годам требует отдельного решения.
